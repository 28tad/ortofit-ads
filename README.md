# ortofit-ads

Работа с Яндекс.Директом через API: выгрузка статистики в CSV и описание
кампаний в YAML с предварительным просмотром изменений.

> **У аккаунта сейчас доступ к API только на чтение.** Методы записи
> (`add`/`update`/`suspend`/`resume`) в коде реализованы, но Директ их отклоняет.
> Поэтому `src/plan.py` по умолчанию работает в режиме предварительного просмотра,
> а применение спрятано за флагом `--apply` и требует подтверждения вводом «да».

## Установка

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Токен кладётся в `.env` в корне проекта:

```
YANDEX_DIRECT_TOKEN=y0__xxxxxxxxxxxxxxxxxxxx
```

Без кавычек и без точки с запятой — `.env` не язык программирования, любой лишний
символ станет частью значения токена. Файл в `.gitignore` и на GitHub не попадает.

## Выгрузка статистики

```bash
# за период
python -m src.fetch --from 2026-01-01 --to 2026-08-04

# за всё время
python -m src.fetch --all-time

# суммы без НДС (по умолчанию — с НДС, как в счёте)
python -m src.fetch --all-time --no-vat
```

Результат:

| Файл | Тип отчёта | Что внутри |
|---|---|---|
| `data/days.csv` | `CUSTOM_REPORT` | Date, CampaignName, AdNetworkType, Impressions, Clicks, Ctr, Cost, AvgCpc, Conversions, CostPerConversion, BounceRate |
| `data/queries.csv` | `SEARCH_QUERY_PERFORMANCE_REPORT` | Date, CampaignName, Query, Impressions, Clicks, Ctr, Cost, Conversions |

Оба файла перезаписываются целиком при каждом запуске.

## Описание кампании и предварительный просмотр

Кампания описывается в YAML — `campaigns/arenda-poisk.yaml`. Структура становится
версионируемой: видно, что и когда менялось, и можно откатиться.

```bash
# предварительный просмотр: только читает аккаунт, ничего не отправляет
python -m src.plan campaigns/arenda-poisk.yaml

# применение: печатает план и требует подтверждения вводом «да»
python -m src.plan campaigns/arenda-poisk.yaml --apply
```

Без `--apply` скрипт печатает заголовок «РЕЖИМ ПРЕДВАРИТЕЛЬНОГО ПРОСМОТРА» и итог
вида `будет создано: 1 кампания, 3 группы, 12 фраз, 3 объявления`, после чего
завершается. Методы записи в этом режиме недостижимы — не «не вызываются», а
находятся за веткой, до которой исполнение не доходит.

С `--apply` подтверждение обязательно и читается только с терминала: перенаправить
ввод (`echo да | ...`) нельзя, скрипт откажется. Это защита от применения из
скрипта или по невнимательности при копировании команды.

Сличение идёт по именам: кампания по `name`, группа по `(кампания, name)`, фраза по
`(группа, текст)`, объявление по `(группа, title)`. Что есть в аккаунте, но нет в
файле, показывается в отдельном разделе, но **не удаляется** — удаление должно быть
отдельным осознанным действием, а не побочным эффектом синхронизации.

### Валидация

Перед построением плана проверяются лимиты Директа. При нарушении печатается имя
группы и фактическая длина, план не строится, код возврата 1.

| Что | Лимит |
|---|---|
| Заголовок | 56 символов, каждое слово ≤ 22 |
| Второй заголовок | 30 символов |
| Текст | 81 символ |
| Ключевая фраза | 7 слов, слово ≤ 35 символов |

У `Title2` и `Text` Директ на самом деле не считает «узкие» символы `!,.;:"`
(до 15 штук сверх лимита). Проверка здесь строже — прошедшее её объявление Директ
примет гарантированно.

## Как устроено

- **`src/direct.py`** — клиент Reports API. Держит заголовки, собирает тело запроса
  и ждёт готовности отчёта: на кодах 201/202 читает заголовок `retryIn`, спит и
  повторяет тот же самый запрос, пока не придёт 200.
- **`src/fetch.py`** — CLI выгрузки. Разбирает аргументы, описывает два отчёта и
  пишет CSV.
- **`src/api.py`** — клиент обычного JSON API v5 (Campaigns, AdGroups, Ads,
  Keywords). Отдельный файл, потому что это другой API: свой эндпоинт, JSON вместо
  TSV и методы вместо параметров отчёта.
- **`src/plan.py`** — CLI сверки YAML с аккаунтом.

## Расхождения между YAML и API

Формат YAML сделан удобным для человека, а не зеркалом API. Три места, где они
не совпадают один-к-одному — `src/plan.py` их разворачивает:

- **Регионы.** В YAML `regions` лежит в секции `campaign`, потому что так их
  задают в голове. В API `RegionIds` — обязательное поле **каждой группы**,
  поэтому список копируется в каждую.
- **Деньги.** В YAML рубли (`daily_budget: 1000`). В API — целые числа, умноженные
  на 1 000 000 (`1000000000`).
- **Стратегия.** В YAML строка «максимум кликов с ограничением средней цены клика».
  В API это `WB_MAXIMUM_CLICKS`, а отключение показов в РСЯ — `SERVING_OFF`
  в секции `Network`.

## Что стоит знать про API

- `Format` поддерживает **только TSV** — CSV получается конвертацией на нашей стороне.
- `ReportName` обязан быть уникальным, поэтому к нему добавляется случайный суффикс.
- При `ALL_TIME` поля `DateFrom`/`DateTo` **недопустимы**, но сам `SelectionCriteria`
  обязателен всегда — отсюда пустой объект `{}`.
- Поле `Query` доступно только в `SEARCH_QUERY_PERFORMANCE_REPORT`, в `CUSTOM_REPORT`
  оно прямо запрещено. Поэтому отчёта два, а не один.
- Заголовки CSV пишутся из списка полей: запрос идёт с `skipColumnHeader: true`,
  и в ответе названий колонок нет.
- Ошибки печатаются с кодом и `RequestId` — по нему поддержка Яндекса ищет запрос.

## Ограничения данных

`Conversions` считает цели Яндекс.Метрики, привязанные к кампании. Если цели не
настроены, колонка будет нулевой — и `CostPerConversion` вместе с ней. Звонки в эти
цифры не попадают вообще, пока не подключён коллтрекинг. Это стоит держать в голове
при анализе: без целей и звонков отчёт показывает расход и трафик, но не результат.

Глубина данных по поисковым запросам у Директа ограничена, поэтому
`SEARCH_QUERY_PERFORMANCE_REPORT` за `--all-time` может вернуть меньше, чем
`CUSTOM_REPORT` за тот же период, или отказать. Если один отчёт упал, второй всё
равно выгрузится — скрипт не прерывается на первой ошибке.

CSV сохраняются в UTF-8 без BOM. Если открывать их в Excel и видно кракозябры —
импортируй через «Данные → Из текста» с явным указанием UTF-8.
