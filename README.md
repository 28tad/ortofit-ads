# ortofit-ads

Работа с Яндекс.Директом через API: выгрузка статистики в CSV и описание
кампаний в YAML с предварительным просмотром изменений.

> **У аккаунта есть доступ на запись** — с 13 августа 2026. Проверено пробами:
> `add`, `update`, `suspend`/`resume`, `archive`/`delete` доступны для кампаний,
> групп, объявлений и фраз.
>
> Раньше отказ Директа служил страховкой от любой ошибки в коде. Её больше нет:
> что напечатано в плане, то и произойдёт в живом кабинете, где крутится бюджет.
> Поэтому `src/plan.py` по умолчанию работает в режиме предварительного просмотра,
> а применение спрятано за флагом `--apply` и требует подтверждения вводом «да»
> с клавиатуры — перенаправленный ввод скрипт отвергает.

## Установка

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Токен кладётся в `.env` в корне проекта:

```
YANDEX_DIRECT_TOKEN=y0__xxxxxxxxxxxxxxxxxxxx
```

Без кавычек и без точки с запятой — `.env` не язык программирования, любой лишний
символ станет частью значения токена. Файл в `.gitignore` и на GitHub не попадает.

## Выгрузка статистики

```bash
# за период
python -m src.fetch --from 2026-01-01 --to 2026-08-04

# за всё время
python -m src.fetch --all-time

# суммы без НДС (по умолчанию — с НДС, как в счёте)
python -m src.fetch --all-time --no-vat
```

Результат:

| Файл | Тип отчёта | Что внутри |
|---|---|---|
| `data/days.csv` | `CUSTOM_REPORT` | Date, CampaignName, AdNetworkType, Impressions, Clicks, Ctr, Cost, AvgCpc, Conversions, CostPerConversion, BounceRate |
| `data/queries.csv` | `SEARCH_QUERY_PERFORMANCE_REPORT` | Date, CampaignName, Query, Impressions, Clicks, Ctr, Cost, Conversions |

Оба файла перезаписываются целиком при каждом запуске.

## Описание кампании и предварительный просмотр

Кампания описывается в YAML — `campaigns/arenda-poisk.yaml`. Структура становится
версионируемой: видно, что и когда менялось, и можно откатиться.

```bash
# предварительный просмотр: только читает аккаунт, ничего не отправляет
python -m src.plan campaigns/arenda-poisk.yaml

# применение: печатает план и требует подтверждения вводом «да»
python -m src.plan campaigns/arenda-poisk.yaml --apply
```

Без `--apply` скрипт печатает заголовок «РЕЖИМ ПРЕДВАРИТЕЛЬНОГО ПРОСМОТРА» и итог
вида `будет создано: 1 кампания, 3 группы, 12 фраз, 3 объявления`, после чего
завершается. Методы записи в этом режиме недостижимы — не «не вызываются», а
находятся за веткой, до которой исполнение не доходит.

С `--apply` подтверждение обязательно и читается только с терминала: перенаправить
ввод (`echo да | ...`) нельзя, скрипт откажется. Это защита от применения из
скрипта или по невнимательности при копировании команды.

Кампания ищется по `campaign.id`, всё остальное — по именам: группа по
`(кампания, name)`, фраза по `(группа, текст)`, объявление по `(группа, title)`.
По имени кампанию искать нельзя: Директ назвал её сам — «Единая перфоманс-кампания
№2 от 09-08-2026», — и до переименования вручную поиск промахивался, а план
предлагал создать всё заново.

Псевдофраза `---autotargeting`, которую Директ заводит в группе сам при включённом
автотаргетинге, из сличения выброшена — иначе она вечно висела бы в разделе
«есть в аккаунте, но нет в файле».

Что есть в аккаунте, но нет в файле, показывается в отдельном разделе, но
**не удаляется** — удаление должно быть отдельным осознанным действием, а не
побочным эффектом синхронизации.

### Валидация лимитов

Перед построением плана проверяются лимиты Директа. При нарушении печатается имя
группы и фактическая длина, план не строится, код возврата 1.

| Что | Лимит |
|---|---|
| Заголовок | 56 символов, каждое слово ≤ 22 |
| Текст | 81 символ |
| Ключевая фраза | 7 слов, слово ≤ 35 символов |

У `Text` Директ на самом деле не считает «узкие» символы `!,.;:"` (до 15 штук
сверх лимита). Проверка здесь строже — прошедшее её объявление Директ примет
гарантированно.

Отдельная проверка запрещает `title2`: в Единой перфоманс-кампании второго
заголовка нет — см. ниже.

### Почему в описании нет второго заголовка

В ЕПК поля `Title2` не существует, но Директ не отвечает ошибкой. Он принимает
запрос, возвращает предупреждение «Параметр не будет применен» и поступает так:

- если `Title` и `Title2` вместе укладываются в 56 символов — **склеивает** их
  в один заголовок через точку;
- если нет — **молча выбрасывает** `Title2`.

Обнаружено 13 августа при создании трёх групп: объявление голеностопа получило
заголовок «Аппарат для разработки голеностопа. Аренда с доставкой», а у плеча и
локтя второй заголовок просто исчез. Склеенный заголовок перестал совпадать с
YAML, и сличение начало предлагать создать дубль объявления.

Поэтому `title2` из описания убран, из сравнения исключён и в запросы не
отправляется, а валидация ловит его возвращение. Нужен второй заголовок по
смыслу — впишите текст прямо в `title`, пока он умещается в 56 символов.

### Проверка текстов на требования к рекламе медизделий

Кампания рекламирует медицинские изделия (РУ РЗН 2013/1334) и уже была отклонена
модерацией по этой тематике. Поэтому тексты дополнительно прогоняются через список
оборотов, за которые Яндекс отклоняет объявления —
[требования к рекламе медицинских изделий](https://yandex.ru/support/direct/ru/moderation/categories/medicine-medical-devices):

| Категория | Обороты |
|---|---|
| Создаёт впечатление, что обращение к врачу не требуется | «не можете ехать в клинику», «без визита к врачу», «без врача», «не нужно в больницу», «замена клинике» |
| Сравнение с другими изделиями и превосходство | «золотой стандарт», «лучший», «эффективнее», «быстрее чем», «дешевле чем» |
| Гарантия эффективности, безопасности, отсутствия побочных | «гарантируем», «без побочных», «безопасно для всех», «излечение», «вылечит» |
| Звучит как медицинская рекомендация | «под ваш диагноз», «назначим», «подберём лечение» |

Проверяются заголовки, вторые заголовки и тексты объявлений, а также уточнения и
подписи быстрых ссылок: модерация смотрит на них наравне с текстом объявления.

Это **предупреждения, а не ошибки** — печатаются с указанием группы и найденной
фразы, но выполнение не прерывается и код возврата остаётся нулевым. Формулировку
выбирает человек; дело скрипта — назвать спорное место, а не решить за автора.
Сравнение регистронезависимое, «ё» и «е» считаются одной буквой, поэтому
«Подберём» и «подберем» ловятся одинаково.

Список литеральный: ищутся ровно перечисленные обороты, без попыток угадать
словоформы. Стем вида «лучш» ловил бы безобидное «улучшение», а ложные
срабатывания быстро приучают не читать предупреждения вовсе.

Чего проверка **не** делает: она не заменяет модерацию и не понимает смысла. Текст
без стоп-слов всё равно может быть отклонён, а формально совпавшая фраза — оказаться
уместной. Предупреждение «Есть противопоказания. Посоветуйтесь с врачом» Директ
добавляет в текстовые объявления сам, вписывать его в тексты не нужно.

## Как устроено

- **`src/direct.py`** — клиент Reports API. Держит заголовки, собирает тело запроса
  и ждёт готовности отчёта: на кодах 201/202 читает заголовок `retryIn`, спит и
  повторяет тот же самый запрос, пока не придёт 200.
- **`src/fetch.py`** — CLI выгрузки. Разбирает аргументы, описывает два отчёта и
  пишет CSV.
- **`src/api.py`** — клиент обычного JSON API v5 (Campaigns, AdGroups, Ads,
  Keywords). Отдельный файл, потому что это другой API: свой эндпоинт, JSON вместо
  TSV и методы вместо параметров отчёта.
- **`src/plan.py`** — CLI сверки YAML с аккаунтом.

## Расхождения между YAML и API

Формат YAML сделан удобным для человека, а не зеркалом API. Три места, где они
не совпадают один-к-одному — `src/plan.py` их разворачивает:

- **Регионы.** В YAML `regions` лежит в секции `campaign`, потому что так их
  задают в голове. В API `RegionIds` — обязательное поле **каждой группы**,
  поэтому список копируется в каждую.
- **Деньги.** В YAML рубли (`weekly_budget: 3500`, `max_cpc: 60`). В API — целые
  числа, умноженные на 1 000 000.
- **Стратегия.** В YAML строка «максимум кликов с ручными ставками». В API это
  структура `BiddingStrategy`, отключение показов в РСЯ — `SERVING_OFF`
  в секции `Network`.
- **Минус-фразы.** В Единой перфоманс-кампании общего списка на кампанию нет, они
  задаются на **каждой группе**. В YAML один набор объявлен якорем `&negatives`
  и подставляется в группы через `*negatives`, чтобы не держать 34 строки трижды.

## Что тут за кампания

№713404098 — **Единая перфоманс-кампания**: классические текстово-графические
кампании в этом аккаунте недоступны. Отсюда несколько особенностей, о которые
легко споткнуться:

- API v5 отдаёт её как `Type: TEXT_CAMPAIGN`. Значения `UNIFIED_PERFORMANCE` в API
  просто нет, поэтому `campaign.type` в YAML описывает интерфейс, а не ответ API,
  и **не сличается** — иначе была бы вечная ложная разница.
- Ставка (`max_cpc`) и минус-фразы живут на группах, а бюджет — недельный, а не
  дневной.
- `campaigns.get` в текущем наборе полей не отдаёт ни недельный бюджет, ни
  площадки, ни цели, ни атрибуцию. В YAML они записаны как желаемое состояние и
  сверяются глазами в интерфейсе; скрипт сличает только имя, регионы групп,
  минус-фразы, фразы и тексты объявлений.
- `campaign_payload()` умеет собирать только `TEXT_CAMPAIGN`. На любом другом типе
  он падает с явной ошибкой — чтобы `--apply` не создал вместо ЕПК что-то другое.
  Такие кампании заводят руками, а скрипт сверяет содержимое.

## Жизненный цикл объявления, созданного через API

Объявление, созданное методом `ads.add`, **само показываться не начнёт**. Полный
путь — три состояния, и только первый переход делается вручную:

```
OFF/DRAFT  ──ads.moderate──▶  OFF/MODERATION  ──сам Директ──▶  ON/ACCEPTED
```

- **`OFF/DRAFT`** — сразу после `ads.add`. Объявление существует, но лежит
  черновиком: показов нет, деньги не тратятся, в интерфейсе группа выглядит
  пустой. На модерацию оно не уходит само — это главная ловушка.
- **`OFF/MODERATION`** — после `api.moderate_ads([...])`. Метод принимает только
  статус `DRAFT`.
- **`ON/ACCEPTED`** — после одобрения. `State` переключается из `OFF` в `ON`
  **автоматически**: `ads.resume` вызывать не нужно.

Последний пункт проверен 13 августа 2026 на трёх объявлениях. Документация связь
`State` и `Status` не описывает, так что это наблюдение, а не цитата — если
однажды объявление зависнет в `OFF/ACCEPTED`, значит поведение изменилось и
понадобится `ads.resume`.

Переименование кампании (`campaigns.update` с полем `Name`) состояния не меняет:
кампания как была `ON/ACCEPTED`, так и остаётся.

## Что выяснено опытом, а не из документации

Документация Директа местами неполна, а местами прямо неверна. Всё ниже проверено
запросом к живому аккаунту:

| Что | Документация | Как на самом деле |
|---|---|---|
| `LocationOfPresenceName` в `CUSTOM_REPORT` | числится недоступным | **работает** |
| `Title2` в ЕПК | не оговорено | поля нет: склеивается с `Title` или выбрасывается |
| Статус после `ads.add` | не оговорено | `DRAFT`, нужен явный `ads.moderate` |
| `State` после одобрения | не оговорено | переключается в `ON` сам |

Отсюда правило для этого проекта: **прежде чем поверить документации о наличии или
отсутствии поля — отправить пробный запрос.** Он стоит несколько баллов и одну
минуту, а ошибка в обратную сторону стоит выдуманного поля в коде, который потом
молча не работает.

Безопасная проба метода записи: послать запрос с заведомо несуществующим `Id=1`
или без обязательных полей. Отказ по правам (`код 58`) выглядит иначе, чем отказ
по содержимому (`код 8000`) или «объект не найден» (`код 8800`) — по типу ошибки
видно, дошёл ли запрос до валидации, и при этом ничего не меняется.

## Что стоит знать про API

- `Format` поддерживает **только TSV** — CSV получается конвертацией на нашей стороне.
- `ReportName` обязан быть уникальным, поэтому к нему добавляется случайный суффикс.
- При `ALL_TIME` поля `DateFrom`/`DateTo` **недопустимы**, но сам `SelectionCriteria`
  обязателен всегда — отсюда пустой объект `{}`.
- Поле `Query` доступно только в `SEARCH_QUERY_PERFORMANCE_REPORT`, в `CUSTOM_REPORT`
  оно прямо запрещено. Поэтому отчёта два, а не один.
- Заголовки CSV пишутся из списка полей: запрос идёт с `skipColumnHeader: true`,
  и в ответе названий колонок нет.
- Ошибки печатаются с кодом и `RequestId` — по нему поддержка Яндекса ищет запрос.

## Ограничения данных

`Conversions` считает цели Яндекс.Метрики, привязанные к кампании. Если цели не
настроены, колонка будет нулевой — и `CostPerConversion` вместе с ней. Звонки в эти
цифры не попадают вообще, пока не подключён коллтрекинг. Это стоит держать в голове
при анализе: без целей и звонков отчёт показывает расход и трафик, но не результат.

Глубина данных по поисковым запросам у Директа ограничена, поэтому
`SEARCH_QUERY_PERFORMANCE_REPORT` за `--all-time` может вернуть меньше, чем
`CUSTOM_REPORT` за тот же период, или отказать. Если один отчёт упал, второй всё
равно выгрузится — скрипт не прерывается на первой ошибке.

CSV сохраняются в UTF-8 без BOM. Если открывать их в Excel и видно кракозябры —
импортируй через «Данные → Из текста» с явным указанием UTF-8.

### Цифры за свежие дни меняются задним числом

Дважды наблюдалось за неделю, так что это правило, а не случайность:

- **Текущий день неполон.** 10 августа днём показывал 16 показов, 5 кликов
  и 411,56 ₽; к закрытию стало 35, 7 и 534,08 ₽ — рост в полтора-два раза.
  Сравнивать дни между собой можно только когда они закрыты.
- **Конверсии досчитываются и после закрытия дня.** За 10 августа цель «Отправил
  контактные данные» показывала 1 достижение сутки спустя и 2 ещё через сутки.
  Модель атрибуции `LSCCD` (последний значимый клик, кросс-девайс) пересчитывает
  задним числом несколько дней.

Практический вывод: вывод «заявка пришла не с рекламы» нельзя делать по свежим
данным — она может дойти до отчёта через день-два. Ровно эта ошибка была сделана
11 августа и опровергнута 12-го.

### Разрез по регионам

`LocationOfPresenceName` — регион, где физически находился пользователь, а не
регион таргетинга. Поле группировочное: каждая строка дробится по регионам, и
`days.csv` вырос с 16 строк до нескольких тысяч — старая РСЯ-кампания крутилась
по 4601 региону, из них у подавляющего большинства нулевой расход.

Директ считает разными регионами то, что кажется одним: «Истра» и «Истра
(городской округ)» приходят двумя отдельными строками. При суммировании по
регионам это стоит учитывать.
